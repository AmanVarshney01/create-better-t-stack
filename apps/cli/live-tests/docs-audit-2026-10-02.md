# PR #1267 documentation and type audit

Audit date: 2026-10-02. Scope: every changed source/template, runner module, test, dependency, and generated artifact in [PR #1267](https://github.com/AmanVarshney01/create-better-t-stack/pull/1267). Evidence comes from official documentation, published package types/source, and generated-project checks. Skills were not used as technical evidence.

Documentation describes supported APIs; runtime results below establish the tested combinations. Neither alone establishes correctness of every possible generated stack.

## Auth sessions and SSR

**React Router and Svelte sign-in/sign-up forms and dashboards:** awaiting `refetch()` before navigation uses Better Auth's public session API. The published `AuthQueryState<T>` defines it as `Promise<void>` and updates the session atom before resolving the fetch. Guards respect `isPending` and `isRefetching`; private queries only run with a session. Callback arguments and session/user types remain inferred. Sources: [Better Auth client](https://better-auth.com/docs/concepts/client), [1.7.7 query source and types](https://github.com/better-auth/better-auth/blob/v1.7.7/packages/better-auth/src/client/query.ts), [TanStack dependent queries](https://tanstack.com/query/latest/docs/framework/react/guides/dependent-queries).

**Nuxt `useAuthSession`, middleware, dashboard, login, auth plugin and header:** use the documented `await authClient.useSession(useFetch)` overload. The auth client is instantiated inside the Nuxt plugin for each request and receives only the incoming cookie header on the server. The menu uses the client-store overload inside `ClientOnly`, as Better Auth recommends for client widgets. Dashboard private data is awaited during Vue's server-prefetch lifecycle. Sources: [Better Auth Nuxt integration](https://better-auth.com/docs/integrations/nuxt), [Vue onServerPrefetch](https://vuejs.org/api/composition-api-lifecycle.html#onserverprefetch), [TanStack Vue SSR](https://tanstack.com/query/latest/docs/framework/vue/guides/ssr).

**Why `credentials: "include"`:** the Nuxt frontend and separate API can have different origins, including different localhost ports. Browser fetch defaults to same-origin credentials. Better Auth's Vue `useSession(useFetch)` implementation passes headers, its cache key and watch sources, but does not pass the client's fetch credentials into Nuxt's fetch. The wrapper adds the standard Fetch option while preserving every supplied option. It is redundant but valid for same-origin fullstack apps. SSR cookies are forwarded explicitly; `credentials` does not supply a server-side cookie jar. URL/options/return types are inferred through the official overload. Sources: [Fetch credentials](https://developer.mozilla.org/en-US/docs/Web/API/Request/credentials), [Better Auth Vue implementation](https://github.com/better-auth/better-auth/blob/v1.7.7/packages/better-auth/src/client/vue/index.ts), [Nuxt request fetch](https://nuxt.com/docs/4.x/api/composables/use-request-fetch).

**Solid session adapter:** the existing integration uses Better Auth's framework-independent client store. The initial signal retains the server's unauthenticated pending snapshot during hydration, then subscribes through `onSettled`; the returned unsubscribe function is lifecycle cleanup. `ReturnType<typeof authClient.useSession.get>` preserves the client's session and plugin types rather than defining a replacement Session interface. Sources: [Better Auth client](https://better-auth.com/docs/concepts/client), [Solid 2 lifecycle migration](https://github.com/solidjs/solid/blob/next/documentation/solid-2.0/MIGRATION.md), [Nano Stores subscriptions](https://github.com/nanostores/nanostores#listening-for-changes).

## Hydration and forms

**Solid forms, Nuxt login and todo controls:** disable interaction until the framework's mounted/settled lifecycle has installed listeners. Solid forms use POST so a native submission cannot put passwords in the query string. Nuxt form IDs are explicit and distinct between sign-in and sign-up, using Nuxt UI's official `AuthFormField` type. Sources: [Playwright hydration guidance](https://playwright.dev/docs/navigations#hydration), [Vue onMounted](https://vuejs.org/api/composition-api-lifecycle.html#onmounted), [Nuxt UI AuthForm](https://ui.nuxt.com/docs/components/auth-form), [HTML form method](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/form#method).

**React Router root HTML:** `suppressHydrationWarning` is limited to the `<html>` element modified by next-themes. This is next-themes' documented integration requirement. The browser runner still fails on other hydration warnings and errors. Source: [next-themes integration](https://github.com/pacocoursey/next-themes#with-app).

## Nuxt RPC, native modules and production entry

**Fullstack `orpc.server` plugin:** all ORMs now use the supported `RPCLink`/`createORPCClient` transport, removing the Prisma-specific branch and a handwritten Cloudflare environment assertion. The client annotation is the project's `AppRouterClient`, derived from oRPC's `RouterClient<typeof appRouter>`. Nuxt's request event fetch forwards the request context; the absolute URL supports oRPC 1.x's standard Request construction. Database/router runtime imports stay in Nuxt server routes. Direct `createRouterClient` is an optional SSR optimization, not required for correct oRPC integration. Sources: [oRPC 1.x Nuxt adapter](https://v1.orpc.dev/docs/adapters/nuxt), [Nuxt request fetch](https://nuxt.com/docs/4.x/api/composables/use-request-fetch).

**Separate-backend Nuxt RPC plugin:** captures only cookie headers during plugin initialization, rather than invoking a Nuxt composable later from a transport callback. URL construction respects the selected provider and service binding.

**Nuxt fullstack SQLite config:** libsql selects its platform addon dynamically. Nitro 2's documented `externals.traceInclude` includes the installed native binding in production. Package metadata is validated with Zod and inferred; optional missing-platform modules are ignored only for `MODULE_NOT_FOUND`, while other resolution errors are thrown. There is no hardcoded macOS/Linux architecture or bundle rewriting. Sources: [libsql loader](https://github.com/tursodatabase/libsql-js/blob/main/index.js), [Nitro 2 official externals types](https://github.com/nitrojs/nitro/blob/v2/src/types/rollup.ts), [Node createRequire](https://nodejs.org/api/module.html#modulecreaterequirefilename), [Zod parsing](https://zod.dev/basics).

**Nuxt local/Docker preview:** runs the generated `.output/server/index.mjs` directly, as Nuxt documents for production Node deployments. Source: [Nuxt Node deployment](https://nuxt.com/docs/4.x/getting-started/deployment#nodejs-server).

## Deployment URLs and official types

**Vercel configuration and shared URL helper:** the SSR web service declares a URL binding to the server service. Vercel documents that these bindings are deployment-aware and bypass deployment protection for service-to-service traffic. The helper resolves a relative `api` path against the binding, preserving any binding path prefix. Browser requests continue to use their own deployment origin. Sources: [Vercel bindings](https://vercel.com/docs/services/bindings), [Vercel Services](https://vercel.com/docs/services), [URL resolution](https://developer.mozilla.org/en-US/docs/Web/API/URL/URL).

The audit replaced handwritten service/binding/rewrite interfaces with `ServiceConfig`, `Services` and indexed official rewrite types from published `@vercel/build-utils@14.14.0`. This import is type-only and the package is a development dependency. JSON serialization avoids asserting those official interfaces into the generator's JSON type. The URL helper now uses Node's `process.env` types instead of a handwritten `globalThis.process` assertion. Sources: [Vercel published types](https://github.com/vercel/vercel/blob/main/packages/build-utils/src/types.ts), [Node globals](https://nodejs.org/api/globals.html#process).

**React, Svelte, Astro and Nuxt auth URLs:** append `auth` to the helper's resolved API base for combined Vercel deployments. The audit's new behavioral test exposed that absolute `/api/auth` resolution discarded a service-binding path prefix in the first three frameworks. That is fixed. Better Auth supports full base URLs including custom auth paths. Sources: [Better Auth base URLs](https://better-auth.com/docs/concepts/client#create-client-instance), [Vercel relative binding URL example](https://vercel.com/docs/services/bindings).

The URL tests now provide one consistent process environment, matching a real runtime. They verify browser, Docker, preview and internal binding URLs without changing their existing expected behavior.

The standalone Prisma-hosted runtime test previously reproduced duplicate exports in the built SSR bundle; it passes with this supported release set. An explicit core dependency prevents the adapter's broad peer range from selecting a different core than auth. Sources: [1.7.7 release](https://github.com/better-auth/better-auth/releases/tag/v1.7.7), [adapter package](https://github.com/better-auth/better-auth/blob/v1.7.7/packages/drizzle-adapter/package.json).

This uses supported package-manager dependency overrides, scoped to generated Alchemy workspaces, with preservation of other overrides. No runtime API shim or patched dependency is added. Sources: [published platform-node package](https://registry.npmjs.org/@effect%2fplatform-node/4.0.0-rc.115), [npm overrides](https://docs.npmjs.com/cli/v11/configuring-npm/package-json#overrides), [pnpm overrides](https://pnpm.io/settings#overrides), [Bun overrides](https://bun.sh/docs/pm/overrides).

## Runner and PR review comments

**Providers:** Neon claim create/delete use a case-local context file and validate JSON/env output. Prisma Postgres uses the supported account-free create-db command with a two-hour TTL. Vercel deploy targets, ready state and aliases are validated. Cleanup records only resources created by the runner; unconfirmed Vercel intents remain pending. Sources: [official Neon CLI](https://github.com/neondatabase/neon-pkgs/tree/main/packages/cli#claimable-projects), [Neon context-file option](https://github.com/neondatabase/neon-pkgs/blob/main/packages/cli/README.md), [Prisma create-db](https://docs.prisma.io/docs/postgres/npx-create-db), [Vercel deploy CLI](https://vercel.com/docs/cli/deploy).

**Deployment protection:** production checks use the public project alias without a bypass; preview checks use the protected deployment URL. Public preview access must be denied or redirected to Vercel. Ordinary app redirects no longer count as proof of protection. The audit reproduced a dummy bypass header reaching an external image from the old JavaScript-disabled context. Authorization now bootstraps a scoped cookie with Vercel’s documented `x-vercel-set-bypass-cookie` flow, only at deployment origins and without following bootstrap redirects. Browser, copied SSR and server-only request contexts subsequently use their cookie jars, with no global bypass header. A real browser regression checks external assets and navigation redirects receive neither bypass headers nor cookies. The JavaScript-disabled Nuxt context copies the authenticated browser's storage and proves the dashboard/private RPC data rendered on the server. Sources: [Vercel authentication](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/vercel-authentication), [automation bypass](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/protection-bypass-automation), [Playwright browser contexts](https://playwright.dev/docs/api/class-browser#browser-new-context), [Playwright shared cookie jars and redirect limits](https://playwright.dev/docs/api/class-apirequestcontext).

**Browser verification:** warm-up visits real routes and waits for usable UI using auto-retrying assertions; it does not suppress navigation errors or use discouraged network-idle waits. Assertions cover HTTP status, origins, auth, persistence, todos and database state. Expected cancelled session reads require a successful replacement; other failures are retained. PWA manifest JSON is validated before access and caches are checked for auth/RPC data. Sources: [Vite dependency optimization](https://vite.dev/guide/dep-pre-bundling), [Playwright actionability](https://playwright.dev/docs/actionability), [Playwright assertions](https://playwright.dev/docs/test-assertions), [Web app manifest](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest).

**Commands, state, local servers and database checks:** use Execa, Node and Bun's official APIs; SQL/HTTP/external JSON rows are validated and types inferred from Zod. Resource/status schemas and `ProjectConfig` are the shared source of domain types. Process cancellation, failed cleanup, locks, source fingerprints and incomplete enumeration keep runs from reporting a false pass. Sources: [Execa cancellation](https://github.com/sindresorhus/execa/blob/main/docs/termination.md), [Bun SQL](https://bun.sh/docs/runtime/sql), [Bun SQLite](https://bun.sh/docs/runtime/sqlite), [Zod inference](https://zod.dev/basics#inferring-types).

The three actionable review concerns were verified and corrected:

1. Cleanup attempts every resource despite failures, retains failed records, shares command numbering and registers environment secrets centrally. A regression test fails the first removal and checks that later removal succeeds, failed state remains, separate logs exist and secrets are redacted.
2. Frontend/addon/example `none` sentinels normalize to empty arrays. A regression reproduced the mismatched configuration before the fix and now verifies identical case IDs.
3. Browser startup is lazy inside web verification. A real server-only HTTP test passes with a browser factory that throws if called. The full runner also exercises server-only auth/RPC/todo behavior.

## Validation

Repository checks passed: root formatting/lint, CLI and test typechecks, template-generator typecheck, CLI build/publint, template-generator build/publint, and 86 website/shared-type tests. The default CLI suite passed 803 tests with 57 skips and zero failures. With `BTS_MATRIX_MODE=smoke`, the creation matrix passed 1,087 tests with 57 skips and zero failures.

The opt-in credential-scoping regression passed in Chromium (40 assertions). Default test runs skip this test so server-only use does not require a browser installation:

```sh
BTS_LIVE_BROWSER_TESTS=1 bun test apps/cli/live-tests/protection.test.ts
```

Fresh standalone `solid-v2-prisma-web` and `nuxt-sqlite-fullstack` build samples passed installation, typechecking, builds and HTTP runtime checks. The Solid sample proves its SSR output boots without duplicate exports. Nuxt’s live checks additionally prove authenticated HTML/private RPC data with JavaScript disabled.

[The verification record](./verification-2026-10-02.md) records the selected runtime cases and their result directories. The original 19 local / five Postgres / two Vercel fixtures remain historical evidence; the audit follow-up identifies results for Better Auth 1.7.7 and the matched Solid rc.13 set.

The final Nuxt/Hono/Neon and Next/Hono/Prisma Postgres reruns passed production and protected preview (four deployment stages) with Better Auth 1.7.7 and scoped bypass cookies. Both result databases contain zero pending resources. Prisma Postgres uses its two-hour expiration. Public production runs use no bypass credential; previews first demonstrate deployment protection, then prove real authenticated behavior.
