## Why

When `database: sqlite` is selected, Better-T-Stack always generates the libSQL client, on every runtime. For `runtime: bun` with a local `file:` URL, that means a Promise-returning napi client sits in front of an embedded SQLite file, while Bun ships a synchronous native SQLite driver that Drizzle already supports via `drizzle-orm/bun-sqlite`.

libSQL is the right default and should stay the default: it is the reason a generated project can move to hosted Turso by changing `DATABASE_URL` rather than changing code, and it is the only option that works on `runtime: workers`. But for someone who has chosen Bun and `dbSetup: none`, that portability is being paid for and never used.

I measured the difference on a project generated by the CLI at 3.41.4 (unmodified schema, Better Auth tables). Both drivers ran through Drizzle against identical databases pushed by `drizzle-kit` from the same schema, in separate processes, with warmup, 3,000 operations per case, median of 5 runs:

| operation | bun:sqlite | libsql | speedup |
|---|---|---|---|
| insert user | 125ms | 165ms | 1.32x |
| lookup by id (PK) | 56ms | 88ms | 1.56x |
| lookup by email (unique idx) | 50ms | 82ms | 1.64x |
| update user | 65ms | 119ms | 1.84x |
| session join user | 144ms | 203ms | 1.41x |

End to end over HTTP — `POST /rpc/privateData` through Elysia + oRPC + a real Better Auth session lookup, 500 requests after 100 warmup, asserting a 200 with session data before timing:

| driver | p50 | p95 | mean |
|---|---|---|---|
| bun:sqlite | 0.26ms | 0.38ms | 0.29ms |
| libsql | 0.33ms | 0.48ms | 0.36ms |

About 20% lower request latency, reproduced across two full runs.

I want to be straight about the magnitude, because it argues for an option and not a default change. The saving is 10–20µs per query. The gap is entirely per-call overhead — Promise scheduling and the napi boundary — not engine speed: on an aggregate scan where real work dominates, the two are within noise of each other, which is expected since libSQL is a SQLite fork rather than a reimplementation. For a typical request doing a handful of queries this is invisible next to network time. It is worth having for write-heavy loops, seeding, migrations, and test suites, and worth having for people who picked Bun specifically to avoid extra layers. It is not worth changing anyone's default over.

Environment: Apple M4 Pro (14 core), 24GB, macOS 27.0, Bun 1.4.0, drizzle-orm 0.45.2, @libsql/client 0.17.4. Generated with `--frontend tanstack-start --backend elysia --runtime bun --database sqlite --orm drizzle --api orpc --auth better-auth --db-setup none`.

## What Changes

Add an optional driver selection for SQLite, defaulting to today's behavior so nothing changes for anyone who does not opt in.

- Add a `sqliteDriver` config value with variants `libsql` (default) and `bun`.
- Offer it only when `runtime: bun`, `database: sqlite`, `orm: drizzle`, and `dbSetup` is not `d1` or `turso`. Every other combination keeps libSQL with no prompt.
- Generate `drizzle-orm/bun-sqlite` + `bun:sqlite` in the db template when selected.
- Set `dialect: "sqlite"` instead of `"turso"` in the generated `drizzle.config.ts` when selected.
- Omit `@libsql/client` and `libsql` from generated dependencies when selected.
- Reject the combination during configuration rather than after generation, per the repo's `specs` rule.

### Non-goals

- Changing the default driver. libSQL stays the default everywhere.
- Offering `bun:sqlite` for `runtime: node`, `runtime: workers`, or `dbSetup: turso` / `d1`.
- Adding `better-sqlite3` or any other driver.
- Touching the Prisma SQLite path.
- Any change to the generated Drizzle schema, which is already driver-agnostic (`drizzle-orm/sqlite-core`).

## Sketch of the change

Illustrative only — I have not implemented this, and I would follow whatever shape you prefer. Line references are against `main` at 3.41.4.

**1. `packages/types/src/schemas.ts`** — new schema beside `DatabaseSchema:3`:

```ts
export const SQLiteDriverSchema = z
  .enum(["libsql", "bun"])
  .describe("SQLite driver (bun:sqlite requires runtime: bun)");
```

added to `ProjectConfig` as `sqliteDriver: SQLiteDriverSchema` and to the CLI input schemas as `.optional()`.

**2. `packages/template-generator/templates/db/drizzle/sqlite/src/index.ts.hbs`** — a branch inside the existing `(or (eq runtime "bun") (eq runtime "node") (eq runtime "none"))` case:

```hbs
{{#if (eq sqliteDriver "bun")}}
import { env } from "@{{projectName}}/env/server";
import * as schema from "./schema";
import { drizzle } from "drizzle-orm/bun-sqlite";
import { Database } from "bun:sqlite";

export function createDb() {
	const client = new Database(env.DATABASE_URL);
	client.exec("pragma journal_mode = WAL");

	return drizzle({ client, schema });
}
{{else}}
... existing libsql body unchanged ...
{{/if}}
```

**3. `packages/template-generator/src/processors/db-deps.ts:110`** — in `processDrizzleDeps`:

```ts
if (database === "sqlite") {
  const sqliteDeps: AvailableDependencies[] =
    config.sqliteDriver === "bun" ? [] : ["@libsql/client", "libsql"];
  addPackageDependency({
    vfs,
    packagePath: dbPkgPath,
    dependencies: ["drizzle-orm", ...sqliteDeps],
    devDependencies: ["drizzle-kit"],
  });
  // same guard for the webPkgPath block below
}
```

**4. The generated `drizzle.config.ts`** — `dialect: "turso"` becomes `dialect: "sqlite"` when the driver is `bun`. `drizzle-kit push` works unchanged on `dialect: "sqlite"` under Bun with no `better-sqlite3` install; I verified it creates the Better Auth tables.

**5. `apps/cli/src/prompts/`** — a `sqlite-driver.ts` prompt in the style of `database-setup.ts`, shown only for the combination above, defaulting to libSQL and stating the tradeoff (portability to Turso vs. fewer layers).

**6. Docs and `apps/web/src/lib/constant.ts`** — the new option, plus the stack-builder wiring.

I applied changes 1–4 by hand to a generated project to confirm the shape works: `tsc --noEmit` clean in the db and auth packages, `bun run db:push` created all four Better Auth tables, and a real `sign-up/email` then `sign-in/email` round trip wrote and read `user`, `account`, and `session` through `drizzleAdapter`. Nothing outside those files needed to change — the schema, the Better Auth adapter (`provider: "sqlite"` either way), and `DATABASE_URL` all carried over as-is, including the relative `file:../../local.db` form, which `bun:sqlite` resolves correctly.

## Impact

Scoped to `packages/types` (one schema plus config wiring), the Drizzle SQLite db template, `db-deps.ts`, the generated `drizzle.config.ts`, one CLI prompt, and docs. No effect on Prisma, on non-Bun runtimes, on `dbSetup: turso` / `d1`, or on any existing generated project, since the default is unchanged.

Verification would follow the repo's existing pattern: `bun:test` coverage asserting that `sqliteDriver: "bun"` emits the `bun:sqlite` template and drops the libSQL dependencies, that it is rejected at configuration time for `runtime: node` / `workers` / `dbSetup: turso` / `d1`, and that the generated project typechecks.
