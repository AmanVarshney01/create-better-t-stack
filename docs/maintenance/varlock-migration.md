# Varlock template migration

The generator now emits app-owned Varlock schemas and removes the shared `packages/env` workspace, direct T3 Env dependencies, and direct dotenv dependencies. This is an implementation in progress. Deployment compatibility below must be resolved before merging it as the default.

## Application and package boundaries

Each application owns its schema and generated accessor:

```text
apps/web/.env.schema
apps/web/src/env.ts       # generated by Varlock, not hand-written
apps/server/.env.schema
apps/server/src/env.ts    # generated by Varlock, server schema only
apps/server/src/env.server.ts
apps/server/src/services.ts
packages/db/.env.schema  # imports the owning app's database settings for CLI tools
packages/db/src/config.ts
```

The schema specifies `@generateTsTypes(path=./src/env.ts, exposeEnv=local)`. The filename is our convention; `exposeEnv=local` follows the recommendation for separate application schemas in [Varlock's monorepo guide](https://varlock.dev/guides/monorepos/). Varlock's default is global type augmentation, which would combine keys from unrelated applications.

Before, shared packages imported the app's ambient configuration and initialized themselves:

```ts
// packages/env/src/server.ts — abbreviated former pattern
export const env = createEnv({
  server: { DATABASE_URL: z.string().min(1) },
  runtimeEnv: process.env,
});

// packages/db/src/index.ts
import { env } from "@my-app/env/server";
export const db = createDb(env);
```

Now the application owns loading and client lifetime:

```dotenv
# apps/server/.env.schema — abbreviated example
# @defaultRequired=true
# @defaultSensitive=true
# @generateTsTypes(path=./src/env.ts, exposeEnv=local)
# ---
# @type=string(minLength=1)
DATABASE_URL=
```

```ts
// apps/server/src/env.server.ts — ordinary Node/Bun server
import "varlock/auto-load";
export { ENV as env } from "./env";

// packages/db/src/index.ts — database-specific implementation omitted
export function createDb(config: DatabaseConfig) {
  // Initialize this database adapter using config.DATABASE_URL.
}

// apps/server/src/services.ts — abbreviated generated composition
import { env } from "./env.server";
import { createDb } from "@my-app/db";
import { createAuth } from "@my-app/auth";

const db = createDb(env);
export const auth = createAuth(env, db);
```

Shared database, auth, and payment packages take narrow typed configuration or initialized clients. API contexts live in the owning app and provide the database to shared routers. Shared packages do not import application source or initialize Varlock.

Pass the `ENV` proxy directly when a consumer accepts its shape. Spreading it into `{ ...ENV }` does not copy its configuration keys; an actual signup test caught that mistake in auth initialization.

## Loading and generation

- Root installation runs `varlock codegen --path ...` for each app and the database tool schema. The root `env:generate` command repeats this after schema changes.
- Bun's own dotenv loading is disabled in `bunfig.toml`.
- Node/Bun server bootstrap and database configuration tools import `varlock/auto-load`.
- Vite, Next.js, Nuxt, Astro, and Expo use their official integrations. Node SSR integrations use `ssrInjectMode: "auto-load"` for direct server startup. Vercel and Prisma web artifacts use the documented `resolved-env` mode because their runtime artifacts do not include the Varlock CLI or schema.
- Next's `@next/env` override lives at the workspace root, including pnpm's workspace override. The PWA wrapper wraps the config object inside the Varlock wrapper.
- Native Metro and Babel integrations preserve Bare, Uniwind, and Unistyles configuration.
- Normal `dev`, `build`, and `start` scripts have no `varlock run --` prefix.
- Turbo hashes env files and forwards schema keys and provider selectors in strict mode.

`auto-load` calls the Varlock CLI internally. Production environments need that executable, its dependencies, and the schema; bundling the auto-load module alone is insufficient. See [Node](https://varlock.dev/integrations/javascript/), [Bun](https://varlock.dev/integrations/bun/), and [Vite](https://varlock.dev/integrations/vite/).

## Reproducible runtime checks

```sh
bun run scripts/varlock-smoke.ts
```

This builds the actual CLI, invokes its command-line entry point, installs the generated applications, and removes temporary fixtures afterward. The validation fixtures add synthetic configuration, but do not retrofit a Varlock migration onto the generated projects.

The script checks:

- Bun workspaces and Turbo strict mode builds and types.
- App-local type isolation and selective root schema imports.
- Preview/production env file selection and process overrides.
- Missing-variable failures at build and startup.
- Node/Bun automatic loading and a built Hono handler.
- Absence of synthetic secrets in browser bundles.
- A full Hono/Drizzle/SQLite/tRPC/Better Auth project: schema push, todo create/read, CORS, signup, and an authenticated session.

The runtime check also caught a template mismatch with Better Auth 1.7.3. Its [official upgrade guide](https://better-auth.com/docs/guides/1-7-upgrade-guide) removes the required account `issuer` introduced in 1.7.0–1.7.2. Generated schemas now use the provider/account identity pair without a required issuer column. Existing databases need a separately reviewed schema migration.

The `Varlock Templates` workflow runs these checks. The broader Default Suite and Curated Build Set remain required; a successful build does not establish that every deployment adapter boots correctly.

## Deployment compatibility still blocking merge

1. **Alchemy/Cloudflare — decision:** Keep Alchemy and use `import "varlock/auto-load"` in its Node/Bun deployment script to replace dotenv. The generator already emits this import. Varlock loads and validates deployment configuration into `process.env`; Alchemy can pass resolved values through its normal Worker bindings. This does not require `varlock run --` or an official Alchemy integration. Verify the complete configuration and binding flow before merge. The separate in-Worker Varlock runtime, including console redaction and response leak detection, remains deferred until official integration support tracked in [issue #735](https://github.com/dmno-dev/varlock/issues/735) is available. Do not import the CLI-loading module inside Workers or serialize Varlock's private env graph. See the official [auto-load documentation](https://varlock.dev/integrations/javascript/) and [non-Wrangler deployment guidance](https://varlock.dev/integrations/cloudflare/#non-wrangler-deploy-tools-alchemy-sst-pulumi).
2. **Packaged Node deployments:** Docker templates mount configuration through BuildKit secrets and retain the schema and installed Varlock CLI where the runtime needs them. Next standalone preloads the public `varlock/auto-load` module with Node before starting the generated server. The generated Hono/Node image passes local build, HTTP startup, and missing-variable rejection checks. `scripts/varlock-docker-smoke.ts` passes in CI for Hono, Next.js, Nuxt, and Solid: image builds, HTTP responses, absence of env value files in runtime working directories, and rejection of invalid runtime configuration. Vercel/Prisma web adapters use the official `resolved-env` mode. Solid, React Router, and SvelteKit Prisma artifacts now pass boot checks after copying only their build output outside the workspace; the automatically detected frameworks and live deployment paths still need verification. Server build artifacts can contain resolved secrets: enable `@encryptInjectedEnv` and provide `_VARLOCK_ENV_KEY` at both build and runtime following [encrypted deployments](https://varlock.dev/guides/encrypted-deployments/). Prisma forwards an explicitly supplied encryption key to both stages; Turbo forwards the key in strict mode.
3. **Managed infrastructure:** IaC-provided database URLs and Worker URLs resolve during provisioning. The deployment schema must validate inputs at the right stage without requiring resource outputs beforehand.
4. **Cloudflare request lifetimes:** Verify connection ownership and lifetime in request-scoped services, including supported MongoDB selections, using native Worker bindings. These checks can proceed without waiting for the optional in-Worker Varlock integration.

At code commit `42d2bb8e`, the local Default Suite plus Matrix Smoke passed 1,020 tests, and [all 42 generated install/build samples passed in CI](https://github.com/AmanVarshney01/create-better-t-stack/actions/runs/34073146546). The [Varlock runtime and four Docker checks also passed](https://github.com/AmanVarshney01/create-better-t-stack/actions/runs/34073146514). The Solid/npm fix keeps the vanilla auth-client factory in the shared auth package and passes its URL from the app, avoiding the optional Solid 1 peer conflict without bypassing npm peer checks.

Fresh Next.js, Solid, React Router, and TanStack Router PWA projects were generated through the built CLI under `~/dev/test/varlock-pwa-*`. All four passed production Chromium checks with Varlock enabled: an activated service worker, no installability errors, expected offline content after a network-disabled reload, and HTTP 200 after reconnecting. The three SSR frontends show their offline page; TanStack Router retains its cached application shell. These checks do not establish physical-device or Safari behavior.

No paid infrastructure has been provisioned for these checks. The local Docker daemon was started to execute the generated Hono image. Test containers and their images were removed after verification.

## Environment selector observation in 1.18.0

A local reproduction importing `APP_ENV` from a root schema received the root `.env.local` selector value but did not select the importing app's `.env.preview`. Redeclaring `@currentEnv=$APP_ENV` in the app then rejected the imported selector. App schemas therefore declare their own selector, a supported monorepo layout, and Turbo forwards shared process overrides. Do not rely on the inherited-selector behavior without an upstream-confirmed test.
